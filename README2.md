# Crawl (караул)

## Технологии
- Java 21. 
- Gradle (Kotlin DSL).  
- JCurses — рендер и ввод с клавиатуры (терминальный UI). 
- JSON: сохранения/загрузка (конкретную библиотеку определим позже).  

## Структура репозитория
Проект придерживается стандартного Gradle layout: исходники в `src/main/java`, тесты в `src/test/java`, ресурсы в `src/main/resources`, сборка — в `build/`.

## Архитектура
В README.md (ТЗ проекта) явно предлагается разделять приложение на слои: `presentation`, `domain`, `datalayer` и строить зависимости “к центру”. 

### Clean Architecture (границы и зависимости)
- `domain` — центр системы: сущности и правила игры, не знает про JCurses, JSON и файловую систему. 
- `presentation` и `datalayer` — внешние слои: используют домен, но домен их не импортирует. 
- Интеграция через контракты (ports): домен объявляет интерфейсы (например, `SaveRepository`), внешние слои дают реализации (например, `JsonSaveRepository`). 

### MVP внутри presentation
- `view` — тонкая оболочка над JCurses: рисует и читает нажатия. 
- `presenter` — управляет экранами/режимами и связывает UI с доменом: переводит нажатия в `Command`, вызывает `GameEngine`, отдаёт снимок состояния на рендер. 
- `model` в MVP — это наш `domain` (GameEngine + GameState). 

## Управление и “бег”
Требование: игра пошаговая, но игроку должно быть удобно идти по длинным коридорам без “закликивания”. 

Проблема: в терминальном вводе (curses/JCurses) нет надёжных событий key-up, поэтому “зажал vs кликает” корректно различить сложно. 

### Что делаем
Мы реализуем “привычное удержание” через pending-направление и таймер:

- В `presentation` хранится `pendingDirection`, который может быть пустым (важно, чтобы можно было экстренно остановиться и думать, без фантомного движения).
- Ввод читается постоянно (не блокируемся “на ожидание тика”), и при каждом WASD обновляем `pendingDirection`.
- Игровой цикл тикает с частотой 15 тиков/сек (TPS = 15).
- На каждом тике:
  - если `pendingDirection` пустой → игрок не делает ход (мир стоит, как в turn-based).
  - если `pendingDirection` задан → выполняем ровно **один** шаг (одна команда движения), после чего домен делает “ход врагов”/обновление мира по правилам. 

### Почему не очередь нажатий
Мы намеренно не буферизуем поток нажатий в очередь на 100 команд вперёд, чтобы персонаж не шёл “по инструкции”.  
Вместо этого используется актуальное `pendingDirection`: направление можно менять “на лету”, и следующий тик выполнит шаг уже в новом направлении.

### Как очищаем pending (остановка)
Так как key-up нет, остановка делается правилом “pending живёт недолго”:
- при каждом WASD запоминаем `lastInputTime`.
- если `now - lastInputTime > holdTimeoutMs` → `pendingDirection = empty`.

`holdTimeoutMs` подбираем экспериментально (например, 200–300 мс), но смысл именно такой: перестал приходить ввод — значит игрок отпустил/перестал давить и игра должна остановиться.

## Что пишем (обязательная часть 0–5)
Требования по задачам (0–9) описаны в README.md; здесь фиксируем “крупные блоки работ”, чтобы параллелиться. 

### Domain (`ru.crawl.domain`)
- Сущности и состояние: `Player`, `Enemy` (5 типов), `Item`, `Inventory`, `GameState`, координаты и тайлы. 
- Turn-based цикл: “команда игрока → обновление мира → ход врагов”. 
- Бой: шанс попадания (ловкость), урон (сила + оружие), смерть, лут (сокровища). 
- Генерация уровней: 9 секций (3×3), комнаты случайного размера/позиции, коридоры, проверка связности, старт/финиш. 

### Presentation (`ru.crawl.presentation`)
- `view`: рендер карты/акторов/панелей через JCurses. 
- `input`: маппинг клавиш → доменные команды (`KeyMapper`).  
- `presenter`: главный цикл/экраны (`GamePresenter`, `Screen`), плюс реализация pending-движения (TPS=15).  
- Управление: WASD + клавиши использования предметов, меню выбора (1–9 / 0–9 для оружия). 
- Туман войны и поле зрения (ray casting/Брезенхэм) — после базового перемещения. 

### Data layer (`ru.crawl.datalayer`)
- Сохранение прогресса после уровня: номер уровня + статистика. 
- Загрузка последней сессии: восстановление состояния вплоть до позиций/характеристик сущностей. 
- Таблица рекордов: сортировка по сокровищам. 

## Основные интерфейсы (контракты)
`domain/usecase`:
- `GameEngine` — `step(Command): GameSnapshot`.  
- `Command` — действие игрока (Move/Use/Equip/OpenMenu/ConfirmSelection…).  
- `GameSnapshot` — DTO/снимок для отображения (то, что нужно UI, без JCurses-типов).

`domain/port/out`:
- `SaveRepository` — сохранить/загрузить состояние/рекорды (порт наружу).

`datalayer/json`:
- `JsonSaveRepository` — реализация `SaveRepository` на JSON.

## Пакеты: за что отвечают
- `ru.crawl.app` — вход в приложение: сборка зависимостей, запуск UI, выбор режима (новая игра/продолжить).  
- `ru.crawl.domain` — все правила игры и данные: **!!никаких импортов JCurses/JSON!!**. 
- `ru.crawl.presentation` — взаимодействие с пользователем: ввод, экраны, рендер, игровой цикл (включая pending + TPS).  
- `ru.crawl.datalayer` — IO: JSON, файлы, рекорды.

## Мини-план реализации (чтобы начать писать код без разночтений)

2) Добавить ход врагов после каждого шага игрока (turn-based). 
3) Подключить генерацию уровня и контент (предметы/враги/комнаты). 
4) Подключить сохранения/загрузки через `SaveRepository`. 


## Контракты (важно соблюдать)

### Границы зависимостей
- `domain` не импортирует классы из `presentation` и `datalayer` (ни JCurses, ни JSON-библиотеку, ни файловые пути).
- `presentation` общается с доменом только через `GameEngine`/`Command`/`GameSnapshot` и доменные модели (если нужно).
- `datalayer` реализует доменные порты (интерфейсы) и может зависеть от JSON/файлов, но наружу возвращает **только доменные типы** (или DTO, определённые доменом).

### Контракт доменного движка (обязательный)
Зафиксировать API движка так, чтобы UI всегда работал одинаково:

- `GameEngine#step(Command): GameSnapshot` — единственная точка “сделать ход” (любой ход игрока).  
- `Command` — закрытый набор команд (sealed interface + records / enum+payload), чтобы добавление новой команды было явным изменением API.  
- `GameSnapshot` — **именно снимок для UI**, без JCurses-типов и без ссылок на внутренние изменяемые коллекции.

Правила семантики:
- Один вызов `step` = один ход игрока + все обязательные реакции мира (включая “ход врагов” после игрока, если так решено).  
- `step` не должен блокироваться на ввод/таймер: вся “частота 15 TPS + pendingDirection” — это ответственность `presentation`, а домен просто применяет команду.

### Контракт “бег/удержание” (принятое поведение)
Чтобы все одинаково понимали, где реализуется удержание:
- `presentation` обязуется держать `pendingDirection` (может быть пустым) и решать, когда превращать его в `Command.Move(dir)` с частотой 15 TPS.  
- `domain` не знает слова “удержание”, он знает только “пришла команда Move”.

Это важно: домен остаётся чистым turn-based, а “удобство удержания” — это политика ввода в UI.

### Контракт сохранений (порт наружу)
Минимальный набор, который уже можно зафиксировать (и он масштабируется):
- `SaveRepository` (порт) в `domain.port.out`:
  - `void save(GameState state)` / `GameState loadLast()` (или `Optional<GameState>`)  
  - `void saveHighScores(HighScores scores)` / `HighScores loadHighScores()`

Ключевое правило:
- Домен **всегда** обращается к интерфейсу `SaveRepository`, а конкретная реализация (`JsonSaveRepository`) живёт в `datalayer`.

### Контракт View (чтобы presenter не “лип” к JCurses)
Уже сейчас полезно договориться:
- `View` не содержит игровой логики и не вызывает `GameEngine`.  
- `View` получает на вход данные для рисования (обычно `GameSnapshot` или его часть) и рисует.

Минимальный интерфейс вида:
- `render(GameSnapshot snapshot)`
- `pollInput(): Optional<Key>` или `readInputNonBlocking()` (как договоритесь внутри presentation)
